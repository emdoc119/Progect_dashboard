# 개인 프로젝트 통합 운영 규칙

> 적용 범위: Codex와 Antigravity를 이용해 관리하는 모든 개인 프로젝트
> 기준일: 2026-07-29
> 전역 AI 지침: `/Users/choo/.codex/AGENTS.md`

## 1. 운영 목표

이 규칙의 목적은 여러 프로젝트가 흩어지거나 서로 다른 방식으로 실행되는 문제를 줄이고, 다음 상태를 일관되게 유지하는 것이다.

1. 프로젝트마다 공식 로컬 경로와 GitHub 저장소를 하나씩 둔다.
2. 개발 환경과 실제 운영 서버를 명확히 구분한다.
3. 지속적으로 켜져야 하는 서비스는 터미널에 의존하지 않는다.
4. 대시보드에서 실제 접속 상태, health 상태와 운영 위치를 확인할 수 있게 한다.
5. 중요한 변경은 문서와 Git에 함께 남긴다.
6. 여러 AI가 작업하더라도 같은 현재 상태와 결정 기록을 공유한다.
7. 토큰을 효율적으로 사용하되 보안과 작업 품질을 낮추지 않는다.

## 2. 프로젝트의 공식 원본

각 프로젝트는 아래 세 가지를 반드시 명확히 한다.

| 항목 | 원칙 |
|---|---|
| 공식 로컬 경로 | `~/.gemini/antigravity/scratch/<project>` 아래 하나만 사용 |
| 공식 원격 저장소 | 프로젝트별 GitHub 저장소 하나를 기준으로 사용 |
| 실제 운영 위치 | Mac Mini, 외부 VPS·클라우드, GitHub Pages 중 하나를 명시 |

- 백업 폴더, IDE 복사본과 예전 개발본을 활성 코드로 사용하지 않는다.
- 같은 이름의 프로젝트가 여러 곳에 있으면 먼저 공식 경로를 확인한다.
- 삭제가 필요한 복제본은 공식 경로와 Git 원격을 확인한 뒤 명시적인 승인 후 정리한다.
- 실제 운영 서버가 외부 클라우드에 있으면 로컬 앱과 동일한 서비스로 간주하지 않는다.

## 3. 서버 운영 원칙

### 3.1 지속 서비스

Mac Mini가 켜져 있는 동안 계속 제공되어야 하는 앱은 다음 조건을 만족해야 한다.

- 터미널 창이나 tmux 세션에 생존을 의존하지 않는다.
- Mac 재부팅 후 자동으로 시작한다.
- 비정상 종료 시 제한된 재시도 정책으로 복구한다.
- 고정된 내부 포트 또는 고정된 서비스 이름을 사용한다.
- 가능한 경우 `/health` 같은 실제 health endpoint를 제공한다.
- 로그 크기 제한과 보존 기간을 설정한다.

권장 관리 순서는 다음과 같다.

1. Docker 기반 앱: Docker Compose의 restart policy
2. macOS 네이티브 지속 서비스: launchd
3. 기존 Node 중심 앱의 과도기 운영: PM2
4. tmux: 개발과 임시 디버깅에만 사용

### 3.2 외부 접속

- 개인 서비스의 기본 외부 접속망은 Tailscale로 한다.
- 외부에서 포트 번호를 각각 기억하는 방식보다 하나의 HTTPS gateway와 앱별 경로 또는 이름을 사용한다.
- 서비스 자체는 가능한 한 loopback에 바인딩하고 gateway만 외부 요청을 받는다.
- 공개 인터넷 노출은 별도 보안 검토와 명시적인 승인 없이 사용하지 않는다.
- Mac Mini의 잠자기 설정 때문에 접속이 끊기지 않도록 전원 운영 상태를 확인한다.

### 3.3 상태 판정

대시보드 상태는 다음 우선순위로 판단한다.

1. 실제 health endpoint 응답
2. 실제 웹 또는 API 응답
3. Docker·launchd·PM2의 서비스 상태
4. 단순 프로세스 존재 여부

프로세스가 살아 있다는 이유만으로 서비스를 `running`으로 표시하지 않는다. 원격 서비스는 로컬에서 시작하려 하지 않고 원격 health 상태만 조회한다.

## 4. AI 작업 분담

### 4.1 메인 오케스트레이터

- 메인은 선택 가능할 때 GPT-5.6 Sol을 사용한다.
- 메인이 요구사항 해석, 계획, 모델 선택, 결과 통합과 최종 검증을 담당한다.
- 작은 수정은 직접 처리하고, 위임이 실제로 시간·품질상 유리할 때만 서브에이전트를 사용한다.

### 4.2 모델 선택 기준

| 작업 | 우선 모델 |
|---|---|
| 아키텍처, 보안, 고위험 변경, 최종 판정 | GPT-5.6 Sol |
| 코드 구현, 반복 수정, 테스트 작성 | Qwen 3.8 Max Preview |
| 큰 코드베이스 탐색, 로그 분석, 문서 요약 | Gemini 3.6 Flash |
| 단순 추출, 목록화, 형식 검사 | Gemini Flash Lite |
| 독립 리뷰 | 주 작업 모델과 다른 계열을 필요에 따라 선택 |

- 2026-07-30부터 Qwen 계열을 사용할 때는 별도 지시가 없으면 Qwen 3.8 Max Preview를 우선한다.
- 해당 모델이 실제 목록에 없으면 다른 Qwen 모델로 조용히 대체하지 않는다.
- Gemini Flash Lite가 제공되지 않으면 Lite를 사용한 것으로 간주하지 않는다.
- 모델 이름의 `Max`와 reasoning effort의 `max`는 별개다.
- 추론 강도는 조사 low~medium, 일반 구현 high, 복잡한 디버깅 xhigh, 중요한 독립 검증 max 이상처럼 작업에 맞춘다.

### 4.3 토큰 절약 원칙

- 사소한 작업은 서브에이전트 없이 메인이 수행한다.
- 모델을 지정한 서브에이전트에는 전체 대화 대신 독립적인 압축 지시서를 제공한다.
- 같은 조사를 여러 에이전트에게 반복시키지 않는다.
- 결과 보고는 변경 파일, 근거, 테스트와 남은 위험 중심으로 받는다.
- history 전체를 매번 읽지 않고 현재 상태 문서를 먼저 읽는다.
- 토큰 절감을 이유로 테스트나 최종 검증을 생략하지 않는다.

## 5. 프로젝트 문서 표준

각 프로젝트는 가능한 한 다음 구조를 사용한다.

```text
project/
├── AGENTS.md
└── docs/
    ├── PROJECT_STATUS.md
    ├── DECISIONS.md
    └── development-history/
        └── YYYY-MM-DD-topic.md
```

### `AGENTS.md`

- 프로젝트 고유 경로, 실행 명령, 금지 사항과 검증 방법을 기록한다.
- 전역 규칙보다 구체적인 프로젝트 규칙을 둔다.

### `PROJECT_STATUS.md`

- 현재 동작 상태, 운영 위치, 알려진 문제와 다음 우선순위를 기록한다.
- 과거 일기를 누적하지 않고 현재 사실만 유지한다.
- 약 150줄 이내를 목표로 한다.

### `DECISIONS.md`

- 중요한 기술·운영 결정을 기록한다.
- 결정, 선택 이유, 고려한 대안과 영향을 간결히 남긴다.

### `development-history/`

- 기능 완료, 장애 복구, 배포 구조 변경 같은 중요한 이정표만 기록한다.
- 목표, 변경 파일, 검증 결과, 남은 문제와 다음 인계 내용을 포함한다.
- 코드 전문, 채팅 전문과 대량 로그를 복사하지 않는다.

## 6. Git 운영 규칙

### 6.1 브랜치

- `main` 또는 `master`는 현재 안정 버전을 나타낸다.
- 중요한 작업은 `codex/작업명` 형식의 작업 브랜치에서 진행한다.
- 사소하고 안전한 변경도 기본 브랜치에 push하기 전에는 변경 범위를 확인한다.

### 6.2 체크포인트와 동기화

다음 변경은 중요한 업데이트로 간주한다.

- 기능 추가 또는 의미 있는 동작 변경
- 장애 수정과 데이터 정합성 수정
- 인증·보안·비밀정보 처리 변경
- 서버, 포트, gateway, 배포와 자동 시작 방식 변경
- 데이터베이스 또는 외부 API 연동 변경
- 아키텍처 결정과 프로젝트 운영 규칙 변경

중요 업데이트의 기본 흐름은 다음과 같다.

```text
작업 브랜치 생성
→ 변경 범위 확인
→ 구현 및 검증
→ 상태·결정·history 문서 갱신
→ 관련 파일만 stage
→ 명확한 메시지로 commit
→ 작업 브랜치를 GitHub에 push
→ 사용자 확인 후 main/master 병합
```

### 6.3 금지 및 중단 조건

- `.env`, 토큰, 비밀번호, 개인정보와 운영 로그를 커밋하지 않는다.
- 사용자 기존 변경을 임의로 덮어쓰거나 관련 없는 변경과 함께 커밋하지 않는다.
- force push, `git reset --hard`와 이력 재작성을 자동으로 실행하지 않는다.
- 테스트 실패, 충돌, 비밀정보 의심 또는 원격 이력 불일치가 있으면 push를 중단하고 보고한다.
- `main` 또는 `master` 병합과 직접 push는 사용자 확인 후 수행한다.

## 7. 보안 규칙

- 인증정보는 `.env` 또는 승인된 secret 저장소에서 관리한다.
- 로그와 오류 응답에서 토큰, 비밀번호와 API key를 마스킹한다.
- 토큰이 로그, 채팅 또는 Git 기록에 노출되면 단순 삭제로 끝내지 않고 해당 토큰을 폐기·재발급한다.
- 외부망에 바인딩하는 관리 화면은 인증 없이 실행하지 않는다.
- 신규 프로젝트 clone·등록 기능은 허용된 루트 경로와 저장소 주소를 검증한다.

## 8. 표준 작업 흐름

### 작업 시작

1. 공식 로컬 경로와 Git 저장소를 확인한다.
2. `AGENTS.md`와 `docs/PROJECT_STATUS.md`를 읽는다.
3. Git 브랜치와 기존 변경사항을 확인한다.
4. 실제 운영 위치와 현재 health 상태를 확인한다.
5. 위험도와 작업 크기에 맞춰 직접 수행 또는 서브에이전트 위임을 결정한다.

### 작업 중

1. 관련 없는 파일을 수정하지 않는다.
2. 한 번에 하나의 가설 또는 변경 단위를 검증한다.
3. 로그와 문서에 비밀정보가 남지 않게 한다.
4. 운영 서비스를 임의로 중단하거나 배포하지 않는다.

### 작업 완료

1. 요청 결과가 실제로 구현됐는지 확인한다.
2. 위험도에 맞는 테스트, 빌드, 정적 검사 또는 health check를 실행한다.
3. 현재 상태와 중요한 결정을 문서에 반영한다.
4. 중요한 변경이면 작업 브랜치에 commit·push한다.
5. 변경 파일, 검증 결과, 제한사항과 다음 작업을 보고한다.

## 9. 예외 처리

- 프로젝트별 `AGENTS.md`가 더 엄격하면 프로젝트 규칙을 따른다.
- 사용자가 현재 작업에서 다른 방식을 명시하면 현재 요청을 우선한다.
- 모델, 도구 또는 외부 서비스가 제공되지 않으면 가능한 척하지 않고 실제 제한과 대안을 보고한다.
- 파괴적 작업, 운영 배포, 외부 메시지 전송과 권한 확대는 요청 범위와 승인을 확인한다.

## 10. 이 문서의 관리

- 운영 원칙이 실제로 변경될 때만 이 문서를 수정한다.
- 일상적인 작업 기록은 이 문서가 아니라 `PROJECT_STATUS.md`와 `development-history/`에 남긴다.
- 전역 규칙과 충돌하지 않도록 `/Users/choo/.codex/AGENTS.md`를 함께 확인한다.
- 이 문서 변경도 중요한 업데이트로 간주하여 Git 체크포인트를 남긴다.
